# Руководство по устранению сбоев

Документ для дежурного администратора. Сценарии отсортированы по симптомам: найдите свой в таблице навигации и переходите к нужному разделу.

## Как пользоваться документом

Каждый сценарий построен одинаково: симптомы → вероятные причины → диагностика → решение → проверка → профилактика. Начинайте с раздела «Первичная диагностика» — он часто сразу указывает на причину.

Все команды `docker compose` выполняются из каталога mailcow:

```bash
cd /opt/mailcow-dockerized
```

**Перед любой операцией, изменяющей данные, сделайте резервную копию:**

```bash
sudo /usr/local/sbin/mailcow-backup
```

## Первичная диагностика

Последовательность, с которой начинается разбор любого инцидента.

```bash
# 1. Сводная проверка: службы, DNS, почтовый поток, безопасность.
#    Самый быстрый способ понять область проблемы.
sudo /путь/к/комплекту/checks/00-full-check.sh

# 2. Состояние контейнеров. Ищем не-running и unhealthy.
cd /opt/mailcow-dockerized && docker compose ps

# 3. Место на диске. Заполнение >90% ломает приём почты и работу БД.
df -h /

# 4. Память и swap. Активный swap означает нехватку RAM.
free -m

# 5. Очередь отправки. Растущая очередь — проблема с исходящей почтой.
docker compose exec postfix-mailcow postqueue -p | tail -20

# 6. Системный журнал за последний час на предмет ошибок ядра и OOM.
journalctl --since '1 hour ago' -p err --no-pager | tail -40
```

Журналы скриптов комплекта лежат в `/var/log/mailstack/`, отчёты проверок — там же с отметкой времени.

## 1. Письма не отправляются

**Симптомы:** письма остаются в папке «Исходящие», получатели ничего не получают, `postqueue -p` показывает растущую очередь.

**Вероятные причины** (по убыванию вероятности):
1. Провайдер VPS блокирует исходящий порт 25
2. IP в чёрном списке, принимающие серверы отклоняют соединения
3. Нет PTR-записи, получатель требует её наличие
4. Проблемы DNS-резолвинга на сервере (`unbound-mailcow`)
5. Переполнен диск, Postfix не может записать в очередь

**Диагностика:**

```bash
cd /opt/mailcow-dockerized

# Очередь и причины задержки: в конце каждой записи текст ошибки от
# принимающего сервера — это главная подсказка.
docker compose exec postfix-mailcow postqueue -p

# Детали по конкретному письму (ID берём из вывода выше).
docker compose exec postfix-mailcow postcat -vq <ID_письма>

# Доступность порта 25 наружу. Если соединение не устанавливается,
# порт заблокирован провайдером.
timeout 10 bash -c 'cat < /dev/tcp/alt1.aspmx.l.google.com/25' && echo "порт 25 открыт" || echo "порт 25 закрыт"

# Журнал Postfix: ищем status=deferred и status=bounced.
docker compose logs --tail 200 postfix-mailcow | grep -E 'status=(deferred|bounced)'

# Проверка DNS-резолвера внутри стека.
docker compose exec unbound-mailcow dig +short gmail.com MX
```

**Решение:**

| Причина в журнале | Действие |
|---|---|
| `Connection timed out` для всех получателей | Запросите разблокировку порта 25 в техподдержке VPS |
| `blocked using zen.spamhaus.org` и подобное | См. раздел [12](#12-ip-в-чёрном-списке-dnsbl) |
| `Helo command rejected: need fully-qualified hostname` | Проверьте `MAIL_HOSTNAME` в `.env` и PTR-запись |
| `No route to host`, резолвинг не работает | `docker compose restart unbound-mailcow` |
| `No space left on device` | См. раздел [6](#6-закончилось-место-на-диске) |

После устранения причины протолкните очередь:

```bash
# Повторная попытка доставки всей очереди.
docker compose exec postfix-mailcow postqueue -f
```

> **Осторожно:** удаление очереди уничтожает письма без возможности восстановления. Применяйте только к заведомо мусорным записям (например, спам-рассылке после взлома).
> ```bash
> # Удалить одно письмо по ID.
> docker compose exec postfix-mailcow postsuper -d <ID_письма>
> ```

**Проверка:**

```bash
# Очередь должна опустеть.
docker compose exec postfix-mailcow postqueue -p
# Отправьте тестовое письмо на внешний адрес и убедитесь, что оно дошло.
```

**Профилактика:** проверяйте порт 25 до установки (`deploy/00-preflight.sh` это делает), настройте оповещение о росте очереди (пример скрипта в [docs/ADMIN.md](ADMIN.md), раздел мониторинга).

## 2. Письма не приходят извне

**Симптомы:** отправители получают отказ или письма просто не появляются в ящике.

**Вероятные причины:**
1. MX-запись отсутствует, неверна или указывает на CNAME
2. Порт 25 закрыт межсетевым экраном
3. Контейнер `postfix-mailcow` не работает
4. Ящик не существует либо превышена квота
5. Письмо попало в папку «Спам»

**Диагностика:**

```bash
# DNS-записи домена: MX, A, SPF, DKIM, DMARC, PTR.
sudo ./checks/20-check-dns.sh

# Доступность порта 25 снаружи — выполняйте с ДРУГОЙ машины.
nc -zv mail.example.com 25

cd /opt/mailcow-dockerized

# Приходят ли соединения вообще: ищем записи connect from.
docker compose logs --tail 300 postfix-mailcow | grep -i 'connect from'

# Поиск судьбы конкретного письма по адресу отправителя.
docker compose logs --tail 500 postfix-mailcow | grep 'sender@example.org'

# Отклонения на этапе приёма.
docker compose logs --tail 300 postfix-mailcow | grep -iE 'reject|550|554'
```

**Решение:**

- MX отсутствует или неверна — внесите запись у регистратора, список готовых записей даёт `./tools/gen-dns-records.sh`. MX обязана указывать на A-запись, не на CNAME.
- Порт закрыт — проверьте `ufw status` и правила `DOCKER-USER`, при необходимости перезапустите `sudo ./security/20-firewall.sh`.
- Контейнер не работает — см. раздел [4](#4-контейнер-не-запускается-или-перезапускается).
- Квота превышена — увеличьте её в панели или через API (см. [docs/ADMIN.md](ADMIN.md)).
- Письмо в спаме — проверьте оценку в журнале Rspamd и папку «Спам» в веб-почте.

**Проверка:** отправьте письмо с внешнего адреса (Gmail, Яндекс) и найдите его в журнале:

```bash
docker compose logs --tail 100 postfix-mailcow | grep -i 'status=sent'
```

**Профилактика:** регулярный запуск `./checks/20-check-dns.sh` — он ловит и исчезновение MX, и расхождение DKIM.

## 3. Исходящие письма попадают в спам

**Симптомы:** получатели находят письма в папке «Спам», Gmail показывает предупреждение о непроверенном отправителе.

**Вероятные причины:**
1. Нет PTR-записи или она не совпадает с именем сервера
2. SPF, DKIM или DMARC не настроены либо настроены неверно
3. IP в чёрном списке
4. Новый IP без истории отправки (репутация не наработана)
5. Содержимое письма похоже на спам

**Диагностика:**

```bash
# Полная проверка DNS, включая сверку опубликованного DKIM с ключом на сервере.
sudo ./checks/20-check-dns.sh
```

Отправьте письмо на https://www.mail-tester.com/ и разберите отчёт — он показывает каждый фактор отдельно. Цель: 10/10.

```bash
# Подписываются ли исходящие письма DKIM.
cd /opt/mailcow-dockerized
docker compose logs --tail 200 rspamd-mailcow | grep -i 'dkim'
```

**Решение:**

| Проблема | Действие |
|---|---|
| PTR не настроена | Настройте rDNS в панели VPS-провайдера — в DNS домена это сделать нельзя |
| DKIM не совпадает с DNS | Обновите TXT-запись значением из `./tools/gen-dns-records.sh` |
| Несколько SPF-записей | Оставьте ровно одну, иначе проверка даёт permerror |
| SPF со `~all` | Смените на `-all` |
| DMARC `p=none` | Переходите поэтапно: none → quarantine → reject |
| IP в DNSBL | См. раздел [12](#12-ip-в-чёрном-списке-dnsbl) |

Новому IP нужна репутация: наращивайте объём постепенно, избегайте массовых рассылок в первые недели.

**Проверка:** повторный тест на mail-tester.com, оценка 10/10. В заголовках полученного письма должны быть `dkim=pass`, `spf=pass`, `dmarc=pass`.

**Профилактика:** ежемесячный прогон `./checks/20-check-dns.sh`, настроенный `rua=` в DMARC для получения отчётов.

## 4. Контейнер не запускается или перезапускается

**Симптомы:** `docker compose ps` показывает состояние, отличное от `running`, либо `unhealthy`, либо счётчик перезапусков растёт.

**Вероятные причины:**
1. Не хватает памяти, процесс убит OOM-killer
2. Нет места на диске
3. Повреждены данные или конфигурация
4. Зависимый контейнер не поднялся (например, MariaDB для php-fpm)
5. Конфликт портов с хостовой службой

**Диагностика:**

```bash
cd /opt/mailcow-dockerized

# Кто не работает.
docker compose ps

# Журнал проблемного контейнера — причина почти всегда в последних строках.
docker compose logs --tail 100 <имя-контейнера>

# Был ли OOM-kill.
docker inspect <имя-контейнера> --format '{{.State.OOMKilled}} {{.State.ExitCode}} {{.State.Error}}'

# OOM-события в системном журнале.
journalctl --since '1 hour ago' | grep -i 'out of memory'

# Конфликт портов.
ss -ltnp | grep -E ':(25|80|143|443|465|587|993) '
```

**Решение:**

```bash
# Перезапуск одного контейнера.
docker compose restart <имя-контейнера>

# Если не помогло — пересоздание (данные в volume сохраняются).
docker compose up -d --force-recreate <имя-контейнера>

# Полный перезапуск стека в правильном порядке зависимостей.
docker compose down && docker compose up -d
```

Дальше по причине: нехватка памяти — раздел [7](#7-закончилась-память-oom), диск — раздел [6](#6-закончилось-место-на-диске), MariaDB — раздел [8](#8-mariadb-не-запускается-или-повреждена).

**Проверка:**

```bash
docker compose ps        # все в состоянии running, без unhealthy
sudo ./checks/10-check-services.sh
```

**Профилактика:** не отключайте `watchdog-mailcow` — он сам перезапускает зависшие службы. Следите за памятью и диском.

## 5. Сертификат Let's Encrypt не выпускается

**Симптомы:** браузер предупреждает о недоверенном сертификате, почтовые клиенты отказываются подключаться, в журнале `acme-mailcow` ошибки.

**Вероятные причины:**
1. A-запись не указывает на этот сервер
2. Порт 80 закрыт или занят — через него идёт проверка домена
3. Достигнут лимит Let's Encrypt (5 неудач в час, 50 сертификатов в неделю на домен)
4. В `ADDITIONAL_SAN` указано имя без корректной DNS-записи

**Диагностика:**

```bash
cd /opt/mailcow-dockerized

# Журнал выпуска: здесь текст ошибки от ACME-сервера.
docker compose logs --tail 100 acme-mailcow

# A-запись должна совпадать с публичным IP сервера.
dig +short A mail.example.com
curl -s https://api.ipify.org; echo

# Порт 80 обязан быть доступен снаружи для HTTP-01 проверки.
ss -ltnp | grep ':80 '

# Срок действия текущего сертификата.
openssl s_client -connect mail.example.com:443 -servername mail.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -dates
```

**Решение:**

- A-запись неверна — исправьте у регистратора, дождитесь распространения, затем `docker compose restart acme-mailcow`.
- Порт 80 закрыт — откройте: `sudo ufw allow 80/tcp`, проверьте правила `DOCKER-USER`.
- Лишние имена в `ADDITIONAL_SAN` — уберите их из `mailcow.conf` (либо создайте для них A-записи) и перезапустите `acme-mailcow`.
- Лимит исчерпан — подождите час. Не перезапускайте контейнер в цикле, это усугубляет блокировку.

```bash
# Принудительный повторный выпуск после исправления причины.
docker compose restart acme-mailcow
docker compose logs -f acme-mailcow   # следим за результатом
```

**Проверка:**

```bash
sudo ./checks/30-check-mailflow.sh   # включает проверку сертификата
```

**Профилактика:** автопродление работает само, но раз в месяц проверяйте срок действия — оповещение можно повесить на скрипт из [docs/ADMIN.md](ADMIN.md).

## 6. Закончилось место на диске

**Симптомы:** почта не принимается, база данных отдаёт ошибки, контейнеры падают.

**Вероятные причины:**
1. Разрослись резервные копии в `/var/backups/mailcow`
2. Логи Docker без ротации
3. Большие почтовые ящики
4. Неиспользуемые образы и volume Docker

**Диагностика:**

```bash
# Общая картина.
df -h /

# Крупнейшие каталоги.
sudo du -sh /var/backups/mailcow /var/lib/docker /opt/mailcow-dockerized 2>/dev/null | sort -h

# Что занимает место в Docker.
docker system df

# Размер почтовых данных и самые большие ящики.
sudo du -sh /var/lib/docker/volumes/mailcowdockerized_vmail-vol-1/_data 2>/dev/null
```

**Решение** (в порядке безопасности — от самого безобидного):

```bash
# 1. Неиспользуемые образы. Безопасно.
docker image prune -f

# 2. Старые резервные копии. Проверьте список ПЕРЕД удалением.
ls -lt /var/backups/mailcow
# Уменьшите BACKUP_KEEP_DAYS в .env, затем:
sudo find /var/backups/mailcow -maxdepth 1 -type d -name 'mailcow-*' -mtime +14 -print
# Убедились в списке — добавьте -exec rm -rf {} +

# 3. Логи journald.
sudo journalctl --vacuum-size=200M
```

> **Опасно:** `docker system prune -a --volumes` удаляет volume с почтой и базой данных. Никогда не запускайте эту команду на почтовом сервере.

Если чистить нечего — расширяйте диск у провайдера, затем растяните файловую систему (`resize2fs` для ext4, `xfs_growfs` для XFS).

**Проверка:**

```bash
df -h /                      # занято менее 80%
docker compose ps            # все контейнеры running
```

**Профилактика:** ротация логов Docker настроена `deploy/20-install-docker.sh` (50 МБ × 3). Настройте оповещение при заполнении выше 80% и выносите копии на внешнее хранилище (см. [docs/ADMIN.md](ADMIN.md)).

## 7. Закончилась память (OOM)

**Симптомы:** контейнеры произвольно перезапускаются, сервер отвечает медленно, в журнале записи об OOM.

**Вероятные причины:**
1. Недостаточно RAM для полного набора служб (ClamAV и Solr требуют много)
2. Отсутствует swap
3. Утечка памяти в одном из процессов

**Диагностика:**

```bash
free -m

# Кого убил OOM-killer.
journalctl --since '24 hours ago' | grep -i 'killed process'

# Потребление по контейнерам.
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}'
```

**Решение:**

```bash
# Вариант 1: отключить тяжёлые компоненты. Правим mailcow.conf.
cd /opt/mailcow-dockerized
sudo sed -i 's/^SKIP_CLAMD=.*/SKIP_CLAMD=y/' mailcow.conf   # антивирус, ~1 ГБ
sudo sed -i 's/^SKIP_SOLR=.*/SKIP_SOLR=y/' mailcow.conf      # поиск по письмам, ~1 ГБ
docker compose up -d
```

Отключение ClamAV убирает антивирусную проверку вложений — взвесьте риск. Rspamd продолжит фильтровать спам.

```bash
# Вариант 2: добавить swap (смягчает, но не заменяет RAM).
sudo fallocate -l 4G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

Вариант 3 и самый правильный при постоянной нехватке — увеличить RAM на VPS.

**Проверка:**

```bash
free -m                      # есть запас доступной памяти
docker compose ps            # контейнеры стабильны, без перезапусков
```

**Профилактика:** минимум 6 ГБ RAM для полного набора служб, мониторинг памяти.

## 8. MariaDB не запускается или повреждена

**Симптомы:** веб-панель отдаёт ошибку базы данных, `mysql-mailcow` в состоянии `restarting`, в журнале сообщения о повреждении таблиц.

> **Сначала резервная копия.** Все действия ниже потенциально разрушительны.

**Вероятные причины:**
1. Некорректное завершение работы (отключение питания, `kill -9`)
2. Нет места на диске
3. Повреждение файлов InnoDB

**Диагностика:**

```bash
cd /opt/mailcow-dockerized

# Причина обычно в последних строках.
docker compose logs --tail 150 mysql-mailcow

# Проверка доступности БД. Пароль берём из mailcow.conf (DBPASS).
source mailcow.conf
docker compose exec mysql-mailcow mysqladmin -u root -p"${DBROOT}" status
```

**Решение:**

```bash
# Шаг 1: обычный перезапуск.
docker compose restart mysql-mailcow

# Шаг 2: проверка и восстановление таблиц.
source mailcow.conf
docker compose exec mysql-mailcow mysqlcheck -u root -p"${DBROOT}" --auto-repair --all-databases
```

Если InnoDB не поднимается, запустите с принудительным восстановлением: добавьте в `data/conf/mysql/my.cnf` строку `innodb_force_recovery = 1` в секцию `[mysqld]`, перезапустите контейнер, снимите дамп базы, затем уберите параметр. Повышайте значение до 4 только при необходимости — уровни выше 3 могут привести к потере данных.

Если восстановить не удалось — восстановление из копии:

```bash
sudo ./tools/restore.sh
```

**Проверка:**

```bash
docker compose ps | grep mysql      # running, healthy
# Веб-панель открывается, список ящиков отображается.
```

**Профилактика:** не выключайте сервер без `docker compose down`, следите за диском, проверяйте свежесть резервных копий.

## 9. Потерян доступ по SSH

**Симптомы:** после применения `security/10-harden-ssh.sh` подключение не устанавливается или отклоняется.

**Вероятные причины:**
1. Изменился порт SSH
2. Отключена парольная аутентификация, а ключ не установлен
3. Ваш пользователь не попал в `AllowUsers`
4. IP заблокирован fail2ban
5. Порт не открыт в межсетевом экране

**Решение через консоль провайдера.** Откройте VNC или серийную консоль в панели VPS — она работает независимо от SSH.

```bash
# Полный откат настроек SSH из комплекта.
rm -f /etc/ssh/sshd_config.d/99-mailstack-hardening.conf
systemctl reload ssh

# Проверка действующих параметров.
sshd -T | grep -E '^(port|permitrootlogin|passwordauthentication|allowusers)'

# Разблокировка своего IP в fail2ban.
fail2ban-client status sshd
fail2ban-client set sshd unbanip <ваш-IP>

# Открыть порт, если закрыт.
ufw allow <порт>/tcp
```

Если доступ есть, но нужен только правильный порт:

```bash
ssh -p <порт> <пользователь>@<сервер>
```

**Проверка:** установите новое подключение из отдельного окна терминала, не закрывая рабочую консоль.

**Профилактика:** всегда держите второе открытое SSH-подключение при изменении настроек SSH — скрипт `10-harden-ssh.sh` об этом предупреждает. Убедитесь в наличии ключа в `~/.ssh/authorized_keys` до отключения паролей. Проверьте доступ к консоли провайдера заранее.

## 10. Забыт пароль администратора mailcow

**Симптомы:** вход в веб-панель с логином `admin` не проходит.

**Решение.** mailcow хранит хэш пароля в таблице `admin` базы `mailcow`. Надёжный порядок действий:

```bash
cd /opt/mailcow-dockerized
source mailcow.conf

# Посмотреть список администраторов.
docker compose exec mysql-mailcow mysql -u root -p"${DBROOT}" mailcow \
  -e "SELECT username, active FROM admin;"
```

Если есть второй администратор, войдите под ним и смените пароль первого через интерфейс — это предпочтительный путь.

Если других администраторов нет, создайте запись с известным паролем. mailcow принимает хэши в формате `{SSHA256}`, сгенерировать их корректно проще всего средствами самого стека:

```bash
# Генерация хэша для нового пароля силами контейнера dovecot.
docker compose exec dovecot-mailcow doveadm pw -s SSHA256 -p 'НовыйНадёжныйПароль'
# Вывод вида {SSHA256}xxxxx... подставляем в запрос ниже.

docker compose exec mysql-mailcow mysql -u root -p"${DBROOT}" mailcow \
  -e "UPDATE admin SET password='{SSHA256}ВСТАВЬТЕ_ХЭШ' WHERE username='admin';"
```

> **Внимание:** правка базы напрямую — операция для крайнего случая. Сделайте резервную копию до начала и убедитесь, что подставляете хэш целиком, вместе с префиксом `{SSHA256}`.

**Проверка:** войдите в панель с новым паролем, сразу включите TOTP (см. [docs/SECURITY.md](SECURITY.md)).

**Профилактика:** храните пароль в менеджере паролей, создайте второго администратора заранее, включите двухфакторную аутентификацию.

## 11. Пользователь не может войти

**Симптомы:** ошибка аутентификации в почтовом клиенте или веб-почте.

**Вероятные причины:**
1. В качестве логина указан не полный адрес, а часть до `@`
2. Неверный пароль
3. Ящик отключён или превышена квота
4. IP пользователя заблокирован `netfilter-mailcow` после серии неудачных попыток
5. Неверные параметры подключения в клиенте

**Диагностика:**

```bash
cd /opt/mailcow-dockerized

# Неудачные попытки входа по конкретному адресу.
docker compose logs --tail 300 dovecot-mailcow | grep -i 'auth failed' | grep 'user@example.com'

# Активные блокировки IP.
docker compose logs --tail 100 netfilter-mailcow | grep -i 'ban'

# Состояние ящика.
source mailcow.conf
docker compose exec mysql-mailcow mysql -u root -p"${DBROOT}" mailcow \
  -e "SELECT username, active, quota FROM mailbox WHERE username='user@example.com';"
```

**Решение:**

- Логин — всегда полный адрес `user@example.com`. Это причина большинства обращений.
- Пароль сбрасывается в панели: Configuration → Mailboxes → Edit.
- Ящик отключён — включите там же. Квота исчерпана — увеличьте.
- IP заблокирован — снимите бан в панели: System → Fail2ban (или дождитесь истечения).
- Параметры клиента: IMAP `993/SSL-TLS`, SMTP `587/STARTTLS`. Полная инструкция — [docs/USER.md](USER.md).

**Проверка:** пользователь входит в веб-почту `https://<MAIL_HOSTNAME>/SOGo/`, затем в клиенте.

**Профилактика:** выдавайте пользователям памятку из [docs/USER.md](USER.md) с готовыми параметрами.

## 12. IP в чёрном списке DNSBL

**Симптомы:** письма отклоняются с упоминанием `blocked using ...` в журнале, проверка `checks/20-check-dns.sh` сообщает о листинге.

**Вероятные причины:**
1. С сервера шла рассылка спама (взлом или скомпрометированный ящик)
2. IP имеет плохую историю от предыдущего владельца
3. Жалобы получателей
4. Ошибочное попадание

**Диагностика:**

```bash
# Какие списки содержат наш IP.
sudo ./checks/20-check-dns.sh

# Проверка по 100+ спискам: откройте в браузере
# https://multirbl.valli.org/lookup/<ваш-IP>.html

# Не идёт ли рассылка прямо сейчас.
cd /opt/mailcow-dockerized
docker compose exec postfix-mailcow postqueue -p | head -40

# Кто отправлял больше всего писем.
docker compose logs --tail 2000 postfix-mailcow | grep -oP 'sasl_username=\K[^ ,]+' | sort | uniq -c | sort -rn | head
```

**Решение:**

1. **Сначала устраните причину.** Если идёт спам-рассылка — раздел [13](#13-компрометация-сервера-или-рассылка-спама). Запрос на удаление без устранения причины приведёт к повторному листингу и ухудшит репутацию.
2. Убедитесь, что PTR, SPF, DKIM, DMARC корректны.
3. Подайте заявку на удаление на сайте списка. У большинства есть self-service форма: [Spamhaus](https://check.spamhaus.org/), [SpamCop](https://www.spamcop.net/bl.shtml), [Barracuda](https://www.barracudacentral.org/rbl/removal-request).
4. Дождитесь обработки — от часов до нескольких дней.

**Проверка:** повторный прогон `./checks/20-check-dns.sh`, письма доставляются.

**Профилактика:** ограничьте лимит писем в час для ящиков, включите TOTP, следите за очередью — резкий рост означает проблему.

## 13. Компрометация сервера или рассылка спама

**Симптомы:** резкий рост очереди, письма от неизвестных отправителей, IP внезапно в чёрных списках, незнакомые процессы, неожиданные входы в журнале.

> **Действуйте по порядку. Не перезагружайте сервер и не удаляйте журналы — потеряете следы и не поймёте способ проникновения.**

**Немедленные действия:**

```bash
cd /opt/mailcow-dockerized

# 1. Остановить исходящую почту, чтобы прекратить рассылку.
#    Приём и доступ к ящикам продолжат работать.
docker compose exec postfix-mailcow postconf -e 'defer_transports = smtp'
docker compose exec postfix-mailcow postfix reload

# 2. Зафиксировать доказательства ДО любых изменений.
mkdir -p /root/incident-$(date +%F)
cd /root/incident-$(date +%F)
docker compose -f /opt/mailcow-dockerized/docker-compose.yml logs --no-color > containers.log
journalctl --since '7 days ago' --no-pager > system.log
ss -tunap > connections.txt
ps auxf > processes.txt
last -50 > logins.txt
docker compose -f /opt/mailcow-dockerized/docker-compose.yml \
  exec -T postfix-mailcow postqueue -p > queue.txt

# 3. Найти скомпрометированный ящик: кто отправлял массово.
grep -oP 'sasl_username=\K[^ ,]+' containers.log | sort | uniq -c | sort -rn | head
```

**Дальнейшие шаги:**

1. **Заблокируйте скомпрометированные ящики** в панели (Configuration → Mailboxes → снять «active»).
2. **Смените все пароли:** администратора панели, всех ящиков, SSH-ключи, пароль API.
3. **Очистите спам из очереди** — только убедившись, что это спам:
   ```bash
   # Удалить письма конкретного отправителя из очереди.
   docker compose exec postfix-mailcow bash -c \
     "postqueue -p | awk '/skompromised@example.com/ {print \$1}' | tr -d '*!' | xargs -r -n1 postsuper -d"
   ```
4. **Проверьте систему** на посторонние изменения: неизвестные пользователи (`cat /etc/passwd`), задания cron (`crontab -l`, `ls /etc/cron.*`), изменённые authorized_keys, сторонние systemd-юниты.
5. **Восстановите нормальную отправку** после устранения причины:
   ```bash
   docker compose exec postfix-mailcow postconf -e 'defer_transports ='
   docker compose exec postfix-mailcow postfix reload
   docker compose exec postfix-mailcow postqueue -f
   ```
6. **При сомнениях в чистоте системы** — разверните новый сервер с нуля и восстановите только данные из копии, сделанной до инцидента (раздел [17](#17-полная-потеря-сервера)).
7. Запросите удаление из чёрных списков (раздел [12](#12-ip-в-чёрном-списке-dnsbl)).

**Чего делать не следует:** перезагружать сервер до сбора данных, удалять журналы, восстанавливать копию поверх работающей системы не разобравшись в способе проникновения (вернёте уязвимость), игнорировать инцидент.

**Профилактика:** TOTP для администратора и пользователей, надёжные пароли, лимиты на отправку, регулярный `./checks/40-check-security.sh`, автообновления. Подробно — [docs/SECURITY.md](SECURITY.md).

## 14. Сбой после обновления mailcow

**Симптомы:** после `tools/update-mailcow.sh` контейнеры не поднимаются, панель недоступна, почта не ходит.

**Диагностика:**

```bash
cd /opt/mailcow-dockerized

docker compose ps
docker compose logs --tail 150 | grep -iE 'error|fatal'

# Текущая и предыдущие версии.
git log --oneline -5
```

**Решение.** Сначала попробуйте достроить обновление — часто причина в незавершённой миграции:

```bash
docker compose up -d
docker compose logs -f --tail 50
```

Если не помогло — откат на предыдущую версию:

```bash
# Коммит до обновления скрипт выводил в журнал: /var/log/mailstack/
git log --oneline -10

# Откат кода и образов.
git checkout <хэш-предыдущего-коммита>
docker compose pull
docker compose up -d --force-recreate
```

> **Важно:** если обновление успело изменить схему базы данных, простой откат кода приведёт к ошибкам. В этом случае восстановите резервную копию, сделанную перед обновлением:
> ```bash
> sudo ./tools/restore.sh
> ```

**Проверка:**

```bash
sudo ./checks/00-full-check.sh
```

**Профилактика:** `tools/update-mailcow.sh` делает копию перед обновлением — не отказывайтесь от неё. Обновляйтесь в часы низкой нагрузки, читайте примечания к выпуску в репозитории mailcow.

## 15. Веб-панель недоступна

**Симптомы:** браузер показывает 502 Bad Gateway, 504 Gateway Timeout или страница не загружается.

**Вероятные причины:**
1. Не работает `php-fpm-mailcow`
2. Не работает `nginx-mailcow`
3. Недоступна база данных
4. Порт 443 закрыт межсетевым экраном
5. Проблема с сертификатом

**Диагностика:**

```bash
cd /opt/mailcow-dockerized

docker compose ps | grep -E 'nginx|php-fpm|mysql'
docker compose logs --tail 80 nginx-mailcow
docker compose logs --tail 80 php-fpm-mailcow

# Ответ с самого сервера — исключаем сетевые проблемы.
curl -k -I https://127.0.0.1/

# Порт открыт?
ss -ltnp | grep ':443 '
```

**Решение:**

```bash
# 502/504 — обычно достаточно перезапустить связку.
docker compose restart php-fpm-mailcow nginx-mailcow

# Если база недоступна — см. раздел 8.
# Если порт закрыт:
sudo ufw allow 443/tcp
sudo systemctl restart mailstack-docker-firewall
```

Почта при недоступной панели обычно продолжает работать — Postfix и Dovecot от панели не зависят. Проверьте это отдельно, чтобы верно оценить масштаб.

**Проверка:**

```bash
curl -k -I https://127.0.0.1/     # ожидаем 200 или 302
sudo ./checks/30-check-mailflow.sh
```

## 16. Высокая нагрузка

**Симптомы:** сервер медленно отвечает, задержки доставки, высокий load average.

**Диагностика:**

```bash
# Нагрузка относительно числа ядер: LA выше числа ядер — перегрузка.
cat /proc/loadavg; nproc

# Потребление по контейнерам.
docker stats --no-stream

# Дисковый ввод-вывод.
which iostat >/dev/null && iostat -x 1 3 || vmstat 1 3

# Не идёт ли массовая рассылка или атака.
cd /opt/mailcow-dockerized
docker compose exec postfix-mailcow postqueue -p | grep -c '^[0-9A-F]'
docker compose logs --tail 500 postfix-mailcow | grep -c 'connect from'
```

**Типичные причины и решения:**

| Причина | Решение |
|---|---|
| ClamAV или Solr съедают CPU и память | Отключите через `SKIP_CLAMD=y` / `SKIP_SOLR=y` (см. раздел [7](#7-закончилась-память-oom)) |
| Активный swap из-за нехватки RAM | Добавьте память |
| Массовая рассылка с сервера | См. раздел [13](#13-компрометация-сервера-или-рассылка-спама) |
| Флуд подключений извне | Правила hashlimit уже ограничивают частоту; проверьте `sudo ./checks/40-check-security.sh` |
| Переиндексация после обновления | Дождитесь завершения, это временно |

**Проверка:** LA ниже числа ядер, очередь не растёт, `./checks/10-check-services.sh` без провалов.

## 17. Полная потеря сервера

**Симптомы:** сервер недоступен, диск утрачен, провайдер не может восстановить.

**Порядок восстановления на новом VPS.** Ключевое условие — наличие резервной копии за пределами утраченного сервера.

```bash
# Шаг 1. Разверните чистый сервер по обычной процедуре.
#        Используйте ТОТ ЖЕ MAIL_HOSTNAME и MAIL_DOMAIN в .env.
git clone <репозиторий> post-server && cd post-server
cp .env.example .env && chmod 600 .env
nano .env

sudo ./deploy/00-preflight.sh
sudo ./deploy/10-bootstrap-os.sh
sudo ./deploy/20-install-docker.sh
sudo ./deploy/30-install-mailcow.sh

# Шаг 2. Доставьте резервную копию на сервер.
#        Пример с внешнего хранилища по SSH:
sudo mkdir -p /var/backups/mailcow
sudo rsync -av backup-host:/backups/mailcow/mailcow-2024-01-15/ /var/backups/mailcow/mailcow-2024-01-15/

# Шаг 3. Восстановите данные. Скрипт покажет список копий и запросит подтверждение.
sudo ./tools/restore.sh

# Шаг 4. Обновите A-запись и PTR на новый IP.
#        A — у регистратора, PTR (rDNS) — в панели нового VPS.
curl -s https://api.ipify.org; echo    # новый IP

# Шаг 5. Сверьте DKIM. Ключ восстановлен из копии, поэтому TXT-запись
#        в DNS должна совпасть с ним. Если нет — обновите запись.
sudo ./tools/gen-dns-records.sh
sudo ./checks/20-check-dns.sh

# Шаг 6. Настройки безопасности и резервное копирование.
sudo ./security/00-harden-all.sh     # держите второе SSH-подключение
sudo ./deploy/50-setup-backup.sh

# Шаг 7. Полная проверка.
sudo ./checks/00-full-check.sh
```

**Проверка:** письма отправляются и принимаются, старая переписка на месте, mail-tester даёт 10/10.

**Профилактика:** храните копии вне сервера (инструкции по rclone и rsync — в [docs/ADMIN.md](ADMIN.md)), периодически проверяйте восстановление на тестовой машине. Непроверенная резервная копия равносильна её отсутствию.
